# Technical alert ownership

SSA (`sirsi-software-admin`) serves the Ma’at software administration role. Horus remains the local workstation observer; Ra remains the routing/orchestration service. Cloud execution must retain those logical identities rather than creating competing mailboxes or stores.

Routine lane-delivery failures and failed broker restoration are proposals addressed to SSA, not owner decisions. An unsuccessful restore is evidence of that failure only: it does not establish RAM exhaustion or authorize reaping unsaved sessions. SSA diagnoses the native host with the responsible software/hardware service and escalates only a specific evidenced human choice.

Repeated observations deduplicate against SSA’s open inbox. Cleared lane conditions resolve only matching Horus notices; unrelated senders and active failures remain untouched. Missing model weights retain their existing, separate owner decision behavior.

Focused normal and race tests pass. A negative control reverting the recipient to `owner` fails the owner-inbox isolation test. Deployment evidence must independently identify the signed executing binary and actual launch process; source tests alone are not deployment.

No cloud worker deployment, provider authentication, funding qualification, Studio enrollment, or complete A2A rollout is implied by this alert-routing correction.
