# ADR-076: Trust-Boundary Law — the A–H checklist every slice reports, and the gate that enforces it

## Status
**Proposed — binding on every Sirsi portfolio repo on merge** — 2026-10-06. Owner directive 2026-10-06: *"Fix and rework those gaps once and for all — not just for FinalWishes."* Steward: Ma'at (𓆄, the QA Sovereign, Rule A17). Companion: Universal Rule 32 in every repo's `CLAUDE.md` §1 and the Development-root `AGENTS.md` Lean Engineering / Completion Law.

## Context

Between 2026-10-05 and 2026-10-06 **every** agent-produced commit in FinalWishes was caught by the automated security sweep on the same recurring classes of defect, and by reviewers on the same process defects. None of them was novel; each had a name and a fix the week before. The lesson is not "review harder" — it is that the portfolio had no written trust-boundary doctrine for agents to satisfy *before* pushing, and no mechanical gate that refuses the known shapes. Each class below actually shipped (or reached review) this week:

| Class | What shipped | Why it is a trust-boundary defect |
|---|---|---|
| **A** Client numbers as bounds | A form row key `250000` made the server allocate 250 000 rows; a web loop ran to `Math.max(...Object.keys(values).map(Number))`. | The client picks how much work the server does. |
| **B** Unbounded output | Attachment pages and "carried text" grew with no ceiling; clipping was quadratic on untrusted input. | A single request can exhaust CPU, memory or storage. |
| **C** Client-supplied provenance | A receipt/hash the client sent was checked only against the bytes the client also sent — anyone could mint a "generated by FinalWishes" document. | Provenance that the untrusted party asserts is not provenance. |
| **D** New path skips sibling gates | A new signing path bypassed the delivery-review check, the email opt-outs and the redirect-URL allowlist that the existing paths all called. | Each resource's gates must be invariants of the resource, not of one handler. |
| **E** Merge instead of replace | `firestore.MergeAll` left stale PII keys from a prior version of a persisted map. | Deleted data that silently survives is a privacy breach. |
| **F** PII on a client-readable path | Form answers were written to a document root that viewer roles can read. | Storage location decides who can read; the field name does not. |
| **G** Silent loss / meaning change | Accepted rows were dropped without a typed refusal; money `'-500'` was "normalised" to `'500'`. | The user's intent was altered without telling anyone. |
| **H** Process | A push went through while the Rule-29 verifier failed, because its exit status was lost in `… \| tail && push`; an agent admitted its own commit to the exemption list; recursion depth caps rejected legitimate input; a cycle detector depended on evaluation order. | The gates themselves were the weakest trust boundary. |

## Decision

### 1. The Law (binding, portfolio-wide)

1. **Bounds come from the server.** Every loop bound, allocation size, page count and iteration count is a server constant or the length of *contiguous, validated* input the server already holds. A number the client sends (a key, an index, a `count`, a `limit`) is never used as a bound; it is validated against a server ceiling and refused above it.
2. **Hard ceilings, typed refusals.** Any output whose size the client can drive (pages, bytes, attachments, carried text, generated rows) has a server ceiling. Above it the server returns a typed refusal (`413`/`422`-class with a stable code), never a truncated success and never unbounded work. No quadratic work on untrusted input.
3. **The server attests provenance.** "Generated by us" is proven by an HMAC or signed token the server minted, or by a server-side record keyed by server-issued id. A hash, receipt, tag or signature the client sends is a *claim*; checking it against bytes the same client sent proves nothing.
4. **A new path calls the same gates.** When a resource already has gate functions (review checks, opt-outs, allowlists, authorization, rate limits), every new path through that resource calls the same functions — **named in the PR** — or the gate is lifted into the shared layer so no path can skip it.
5. **Replace, never merge, persisted user maps.** A map carrying user data is written whole (replace semantics); merge-writes are reserved for server-owned fields. Each such write ships a **stale-key test**: a key present in version N and absent in version N+1 must be gone after the write.
6. **Classify every stored field by reader.** For every field a slice stores, the PR states whether it is client-readable (and by which roles) or server-only. PII, HIPAA and PCI fields are server-only *and* encrypted (envelope encryption, per-tenant AAD); they never live on a document path a viewer role can read.
7. **Never drop, never re-mean.** Accepted input is never discarded silently; a row/answer the server cannot keep produces a typed refusal that names it. Normalisation may change *representation* (whitespace, case, Unicode form) but never *meaning*: a sign, a unit, a currency, a date part, a negative/positive distinction is preserved or the value is refused.
8. **The gates are the first trust boundary.**
   - A verifier gates by **its own exit status**. Never `verifier | tail && push`; a pipe's status is its last command's. Use `set -o pipefail` or no pipe.
   - **Zero self-exemptions.** A change may not add its own commit (or any commit in its range) to a historical-exemption list. The list may only shrink or stay.
   - **Bounded but complete.** Recursive algorithms over user data are written iteratively with explicit cycle detection (visited set keyed by identity) and a ceiling derived from the input's own size — never a fixed depth cap (`depth > 16`) that rejects legitimate deep inputs.
   - **Order-independent evaluation.** A validation or cycle-detection result must not depend on map iteration order, insertion order or evaluation order. Tests shuffle.

### 2. The report (every slice, every PR, every router result)

Each slice reports the checklist below **one line per item**, verdict `satisfied` or `n/a — <reason>`. A missing line is a failing review. `sirsi maat gate --report` prints the skeleton:

```
A. Bounds — every loop/allocation bound is a server constant or contiguous validated input … — verdict
B. Ceilings — hard server ceiling + typed refusal on every client-driven output … — verdict
C. Provenance — server attests (HMAC/signed token/server record); no client-sent hash/receipt trusted … — verdict
D. Sibling gates — new path calls the same gate functions as existing paths: <names> … — verdict
E. Replace-not-merge — persisted user maps replaced whole; stale-key test present … — verdict
F. Reader classification — every stored field classified; PII server-only + encrypted … — verdict
G. No silent loss / no meaning change — typed refusal instead of drop or re-meaning … — verdict
H. Process — verifier exit status gates; zero self-exemptions; bounded-but-complete; order-independent … — verdict
```

### 3. The gate (`sirsi maat gate`, shipped here, adopted by one line)

`internal/maat/trustboundary` + `cmd/sirsi/maatgate.go`. Runs, each step's exit status being the verdict and no step short-circuiting the others:

| Step | What | Fails when |
|---|---|---|
| `traceability` | runs the verifier **as committed at the pushed head** (`git show head:scripts/verify-commit-traceability.sh`, beside the head's exemption list) with `--pull-request <base> <head>` when the head ships it | the script exits non-zero; a read error fails; absence at the head is a reported skip |
| `exemption-growth` | the hash SET in `scripts/traceability-historical-exemptions.txt` at head must be a subset of the set at base (both read as blobs at those commits) | any hash is newly admitted in the range — including an equal-count replacement (H: self-exemption); a git read error also fails |
| `secrets` | `gitleaks detect --log-opts=<base>..<head>` when installed (CI's scan remains authoritative) | gitleaks finds a secret |
| `trust-boundary-lint` | heuristics over the changed Go/TS/shell files read as **blobs at the pushed head** (never the working tree); each finding names its rule letter | any finding; a blob that is missing or unreadable, or Go that does not parse, is an explicit failure (unknown never passes); a reviewed false positive is silenced by `trust-boundary: <reason>` on the line or the line above |

Lint heuristics (tripwires, not proofs): **A** `strconv.*`/`Number()`/`parseInt()` of an object key or client string flowing into `make()`, `Array.from({length})`, `new Array()` or a `for` bound (taint propagates through plain assignment, so `max = n` is caught); **B** `InsertPages`/`AddPage`-family calls inside a loop; **C** provenance-named fields (`hash|receipt|checksum|digest|signature|generatedBy`) on request-shaped types; **D** a per-file `// trust-boundary-gate: F1, F2` directive makes every request-shaped function in that file prove it calls F1 and F2; **E** `firestore.MergeAll` with a map value, `{ merge: true }` on a spread/variable document; **F** sensitive keys (`ssn|dob|answers|formData|passport|bankAccount|…`) inside a document write; **G** `\D`-stripping of a money-named value; **H** depth compares against a literal `< 64`, `verifier | tail` without `pipefail`, `git push --no-verify` in scripts.

Range semantics: `--pre-push` evaluates **every** content-bearing branch ref on stdin and aggregates (one failing ref fails the push; tags and deletions carry no content). A new branch is based at its merge-base with `origin/main`/`origin/master`; when no base can be resolved the push is **refused** — never admitted as "nothing to check".

Adoption:

```sh
# .githooks/pre-push — one line; blocks the push on failure
sirsi maat gate --pre-push || exit 1
# arm the hook for the repo (worktrees share .git/config, so one call covers them all)
sirsi maat gate --install
# survey an existing tree
sirsi maat gate --all --lint-only
```

Pantheon's own `.githooks/pre-push` runs the lint on every push; FinalWishes adopts the full gate (its hook also runs its traceability verifier directly when `sirsi` is absent so the Rule-29 step never depends on a binary).

## Alternatives Considered
1. **Review checklists only, no tool** — rejected: this week proved checklists without a mechanical refusal are forgotten under deadline; the gate makes the known shapes un-pushable.
2. **A full taint analysis (type-checked, cross-file)** — rejected for now: weeks of work, and the shapes that shipped are all caught by file-local heuristics with an explicit allowlist. Revisit if the allowlist comment count climbs.
3. **Fix FinalWishes only** — rejected by owner directive: the defect classes are portfolio-wide; the doctrine lives in Pantheon and every repo inherits it through Universal Rule 32.

## Consequences
- **Positive**: the eight classes are named, reported per slice and refused at push time; the exemption list can only shrink; a pipe can no longer hide a failing verifier.
- **Negative**: heuristic findings on existing code (FinalWishes main and release/court-forms-union-v4: 40 identical findings — 25 Go `firestore.MergeAll` map writes, 7 TS `merge: true` spreads, 6 approval-digest request fields, 2 `birthDate` document fields) must be triaged — reported, not auto-fixed; some legitimate code will carry a `trust-boundary:` reason comment.
- **Risk**: agents silence findings with empty reasons. Mitigation: the reason is reviewed like code; a bare marker is a review failure, and Ma'at may later lint the reason text.
